How I work with Claude

I'm one person doing both design and code, so I need a second set of eyes on every decision. Claude is that for me. It drafts the options I choose from, checks the work against rules I wrote, and tries to break what I think is finished. The decisions stay mine.

I wrote Claude a style guide for how it reports back to me: my request in a box, results on labelled lines, and every question answerable with one letter. That way I can see in a few seconds what I asked, what got done and what it needs from me. Try answering the question.

01

Options before answers

I don't ask Claude for one answer. I ask for two to four options, drawn side by side with one marked as its recommendation, and I reply with a letter. Comparing real options next to each other makes the right one clear much faster than a description does. The canvas is a claude.ai Artifact, a live web page, so I can click through each option and check it in light and dark mode before anything in the product changes. Then the choice gets written down with its date and reason, and building starts.

02

One agent, one job

Each agent is a small AI assistant with exactly one job. I keep them separate because an assistant that builds something and also checks it tends to approve its own work. Each one also runs on the model size its job needs: fast, inexpensive models (Haiku) for checks that run on every change, stronger ones (Opus, Sonnet) for jobs that need judgement. These five check my own app. Open any of them:

Rule guardHaikuChecks every change against the rules I wrote for the project.

It reports every broken rule and fixes none of them, so a report can’t hide a quiet change.

VerifierHaikuRuns the automated tests and reports only what failed.

It runs more than any other agent, so it gets the smallest, cheapest model.

BreakerOpusTries to break a change after it’s finished.

It even plants bugs on purpose to see if the tests catch them (mutation testing). It reports only what it actually broke, with the failing case written out.

WalkerOpusUses the real app on a phone simulator, the way a person would.

It keeps the screenshots to itself and reports back in plain sentences, so the main session stays focused.

ScribeSonnetRecords each decision in the project’s rules after a change merges.

With its date and my own words, so the reason is still there months later.

None of them can save, publish or merge a change. If an agent hits a question it can’t answer, it stops and asks instead of guessing. I’d rather be asked than surprised.

04

What it taught me

  • Ask for options, not answers.A recommendation I can overrule is more useful than one answer I have to argue with.
  • Write the decision down.Otherwise the next session undoes it and sounds sure about it.
  • One agent, one job.Whoever builds something shouldn’t be the only one checking it.
  • Passing tests aren’t proof.Put the bug back and make sure the test fails. If it still passes, it was never protecting anything.
  • Look, then use it.Seeing a screen at phone size and using it on a real phone catches what thousands of tests can’t.
  • It never merges. I do.Every change passes the required checks, and the final approval is mine.
